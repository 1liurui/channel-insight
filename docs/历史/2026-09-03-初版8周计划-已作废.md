# Implementation Plan: 快消渠道运营智能体 (FMCG Channel Ops Agent)

Date: 2026-09-03
Goal: 构建一个面向快消品牌方的渠道运营智能体，支持自然语言问数、指标异动归因、终端陈列稽核三大能力，作为投递快消品牌方数字化中心的核心简历项目。
Architecture: Backend (Python) + Frontend (React) + 本地数仓 + 多模态视觉
Tech Stack: Python 3.13 + FastAPI + LangGraph + DuckDB + Qdrant(embedded) + DeepSeek + Ultralytics YOLO + React/Vite

---

## 硬件约束（决定了所有选型）

| 项 | 实测 | 应对 |
|---|---|---|
| M2 / 8 GB RAM | 决定性约束 | 全栈内存预算 ≤ 1.5 GB |
| Docker 未安装 | 阻断原方案 | 全部改为进程内 / 单二进制，零容器 |
| Python 3.9.6 系统版 | 版本过低 | `uv python install 3.13` 独立管理 |
| MPS 集显，无 CUDA | YOLO 训练慢 | 预训练权重 + 小样本微调；大训练放 Colab |

**内存预算表**

| 组件 | 方案 | 常驻内存 |
|---|---|---|
| 数仓 | DuckDB（进程内列存） | ~200 MB |
| 向量库 | Qdrant embedded (`path=` 本地模式，无服务端) | ~150 MB |
| 稀疏检索 | `bm25s` 进程内，替代 Elasticsearch | ~80 MB |
| Embedding | `bge-small-zh-v1.5` (512维, ~95MB) | ~300 MB |
| FastAPI | uvicorn 单进程 | ~150 MB |
| YOLO 推理 | yolov8n，按需加载 | ~250 MB（非常驻）|
| **合计** | | **~1.1 GB** |

对照原方案（MySQL + ES + Qdrant server + TEI/bge-large）约 6 GB —— 在 8 GB 机器上必然 swap。

### 问数链路（借鉴 shopkeeper-agent，节点对齐）

```
extract_keywords
   ├─▶ recall_column  (Qdrant dense)
   ├─▶ recall_value   (bm25s sparse)   ── 三路并行
   └─▶ recall_metric  (Qdrant dense)
        ▼
merge_retrieved_info → filter_metric → filter_table → add_extra_context
        ▼
generate_sql → validate_sql ──(失败)──▶ correct_sql ──┐
        ▼                                             │
     run_sql ◀────────────────────────────────────────┘
```

### 归因链路（本项目原创，简历核心亮点）

```
locate_metric      定位待归因指标与对比周期
   ▼
decompose_dimension  逐维度计算贡献度（区域/经销商/渠道/SKU/新老店）
   ▼
drill_down          对 top 贡献维度递归下钻（最多 3 层）
   ▼
synthesize          生成结论：谁拖的、拖了多少、建议动作
```

**贡献度算法**（不是让 LLM 瞎猜，是算出来的 —— 这点面试必问）：
对维度 d 的取值 i，销售额变动贡献 `C_i = (V_i,t1 - V_i,t0) / (V_t1 - V_t0)`，
按 |C_i| 降序，累计贡献超过 80% 的取值即为主因。LLM 只负责把算好的数字翻译成业务语言。

## 快消数据模型（星型，这是"懂行"的证明）

### 维度表

| 表 | 关键字段 | 说明 |
|---|---|---|
| `dim_product` | sku_id, 品牌, 品类, 子品类, 规格, 口味, 包装形态, 建议零售价, 保质期天数 | 品类覆盖：瓶装水/无糖茶/含气饮料/功能饮料/啤酒/坚果炒货/膨化食品/个护 |
| `dim_dealer` | dealer_id, 名称, 层级(一级/二级), 大区, 省区, 城市 | 深度分销体系 |
| `dim_store` | store_id, 名称, 渠道类型, 城市, 所属经销商, 门店等级, 开户日期 | 渠道类型：便利店/小超市/夫妻店/餐饮/KA/特通 |
| `dim_rep` | rep_id, 姓名, 所属区域, 负责经销商 | 业务代表 |
| `dim_date` | date, 年, 月, 周, 是否节假日, 季节 | 饮料季节性极强，必需 |

### 事实表

| 表 | 粒度 | 关键字段 |
|---|---|---|
| `fact_sales` | 日 × 门店 × SKU | 出货量, 出货额, 动销量, 动销额 |
| `fact_visit` | 拜访事件 | visit_id, date, rep_id, store_id, 是否到店, 拜访时长, 计划标记 |
| `fact_display_audit` | 稽核事件 | audit_id, visit_id, store_id, 照片路径, 本品排面数, 竞品排面数, SOS, 是否合规, 不合规原因 |
| `fact_promo_cost` | 日 × 门店 × 活动 | 活动id, 费用类型(陈列费/堆头费/买赠), 金额 |
| `fact_inventory` | 日 × 门店 × SKU | 期末库存, 生产日期, 剩余效期天数 |

### 业务口径知识库（RAG 的真正用武之地）

快消最真实的扯皮点就是"这个指标到底怎么算"。以下写入 `conf/metrics.yaml` 并入向量库：

| 指标 | 口径 |
|---|---|
| 铺市率 | 期内有动销的网点数 / 覆盖网点总数 |
| 动销率 | 期内有销售的 (SKU,门店) 组合数 / 应铺 (SKU,门店) 组合数 |
| 单店产出 | 动销额 / 有动销门店数 |
| 排面占比 SOS | 本品排面数 / 货架总排面数 |
| 拜访达成率 | 实际到店拜访数 / 计划拜访数 |
| 费效比 ROI | (活动期增量动销额) / 促销费用 |
| 库存周转天数 | 期末库存量 / 期内日均出货量 |
| 临期占比 | 剩余效期 < 1/3 保质期的库存量 / 总库存量 |

## 数据来源策略

| 层 | 来源 | 说明 |
|---|---|---|
| 销量骨架 | **M5 (Walmart)** FOODS 品类子集 | 真实日销、价格、促销、节假日。降采样至 ~300 SKU × 40 店 × 2 年，控制在 DuckDB 可轻松处理的量级 |
| 促销响应 | **Dunnhumby Complete Journey** | 做费效比 / 促销归因 |
| 货架图像 | **SKU110K** (11,743 张真实货架图) | 排面检测训练与评测 |
| 渠道侧 | **规则生成器**（非 LLM 瞎造） | 按深度分销规则生成经销商/终端/拜访/费用，参数化、可复现、可解释 |

> 面试话术：销量与图像用真实公开数据集，渠道结构用**基于业务规则的参数化生成器**（不是 LLM 随机编），生成逻辑可解释、种子固定可复现。

## 里程碑（8 周，每周可独立交付）

### Week 0 — 环境与骨架（半天）
**交付物**：能跑通一次 LLM 调用 + DuckDB 建库 + Qdrant embedded 写入读出。

- T0.1 `uv python install 3.13` + `uv init` + 依赖锁定
- T0.2 LLM provider 抽象层，跑通 hello world
- T0.3 DuckDB 建库 + `ddl.sql` 执行
- T0.4 Qdrant embedded 模式验证（`QdrantClient(path=...)`，确认无需服务端）
- T0.5 bge-small-zh 本地加载，验证内存占用 < 400 MB

**验收**：`uv run python -m app.smoke` 输出四项全绿。

### Week 1 — 快消数仓
**交付物**：一个装满快消数据的 DuckDB，能手写 SQL 查出"华东区 7 月无糖茶铺市率"。

- T1.1 星型模型 DDL（5 维表 + 5 事实表）
- T1.2 M5 数据下载与降采样（300 SKU × 40 店 × 2 年）
- T1.3 M5 品类 → 快消 SKU 映射表（FOODS → 饮料/零食品类体系）
- T1.4 渠道侧规则生成器：经销商 → 终端 → 拜访 → 费用，固定随机种子
- T1.5 `metrics.yaml` 8 个核心指标口径 + 对应 SQL 片段
- T1.6 手写 10 条基准 SQL 验证数据合理性（铺市率在 60-85% 之间等业务常识校验）

**验收**：10 条基准 SQL 全部返回业务上合理的数值。

### Week 2 — 问数链路
**交付物**：命令行输入自然语言，输出正确 SQL 与结果。

- T2.1 `AgentState` 与图骨架
- T2.2 extract_keywords 节点 + prompt
- T2.3 三路并行召回（dense 字段/指标 + sparse 取值）
- T2.4 merge → filter_metric → filter_table → add_extra_context
- T2.5 generate_sql + prompt（注入口径定义与表结构）
- T2.6 validate_sql：DuckDB `EXPLAIN` 语法校验 + 表/字段白名单 + 禁止 DDL/DML
- T2.7 correct_sql 重试环（最多 2 次）
- T2.8 run_sql + 结果格式化

**验收**：手工 20 个问题，至少 14 个返回正确结果。

### Week 3 — 评测体系（简历分水岭）
**交付物**：一份带数字的评测报告。绝大多数候选人没有这一步。

- T3.1 构造 100 条测试集：问题 / 标准 SQL / 标准结果 / 难度标签（单表/多表join/嵌套/指标计算）
- T3.2 Execution Accuracy 评测脚本（比对结果集，不比对 SQL 字符串）
- T3.3 消融实验：① 无口径知识库 ② 无混合检索只用 dense ③ 无 validate/correct 环
- T3.4 错误归因分析：把失败 case 分类（召回错/口径错/语法错/逻辑错）
- T3.5 输出 `eval/REPORT.md`

**验收**：主方案 EX ≥ 75%，且三组消融都显著低于主方案（证明每个模块都有价值）。

### Week 4 — 归因链路
**交付物**：问"华东无糖茶 7 月动销环比跌 12% 是谁拖的"，能给出带数字的归因结论。

- T4.1 locate_metric：从问题解析出指标、对比周期、筛选范围
- T4.2 decompose_dimension：按 5 个维度并行算贡献度
- T4.3 drill_down：对主因维度递归下钻，最多 3 层，带剪枝
- T4.4 synthesize：把贡献度数字翻译成业务结论 + 建议动作
- T4.5 归因结果可视化数据结构（供前端画瀑布图）

**验收**：构造 10 个已知答案的异动场景（人为在数据里埋因），归因命中 ≥ 8 个。

### Week 5-6 — 陈列稽核（多模态）
**交付物**：上传一张货架照，输出排面数、SOS、合规判定、整改建议。

- T5.1 SKU110K 下载与格式转换（Ultralytics YAML）
- T5.2 yolov8n 微调（M2/MPS 上小样本；若太慢转 Colab 训练后下载权重）
- T5.3 排面检测评测：mAP@50、计数误差率
- T5.4 VLM 品牌判定：对检测框裁剪后批量送 VLM，判定品牌/竞品/口味
- T5.5 合规规则引擎：黄金位占比、最小排面数、陈列协议符合性
- T5.6 稽核结果回写 `fact_display_audit`，与问数链路打通（"上月华东陈列合规率"能问出来）

**验收**：mAP@50 ≥ 0.55，排面计数误差 ≤ 8%，稽核结果可被问数链路查询。

### Week 7 — MCP 化 + 前端
**交付物**：Claude Desktop / Cursor 能直接接入你的快消数仓。

- T7.1 DW-MCP：暴露查询、指标计算工具
- T7.2 Meta-MCP：暴露口径检索工具
- T7.3 CV-MCP：暴露稽核工具
- T7.4 React 前端：SSE 流式对话 + Agent 执行过程可视化 + 归因瀑布图
- T7.5 图片上传稽核界面

**验收**：在 Claude Desktop 中配置 MCP 后，能直接问出快消指标。
