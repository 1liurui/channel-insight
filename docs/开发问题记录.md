# 开发问题记录

> 项目：业务数据问数与归因智能体
> 用途：面试素材库 + 复盘学习。按问题类型组织，不按时间顺序。
> 收录标准：**能讲出根因**的问题才收录。改个参数就好的不算。
> 标 ⭐ 的是面试可以主动抛出来讲的。

---

## 一、数据真实性

真实感不是靠加噪声，是靠**把业务上"为什么会有缺口"的机制建进生成器**。
三个越界指标全部指向同一类错误：把某个业务约束当成了理所当然。

### 1.1 ⭐ 品牌级铺市率 99.6%

**现象** 基准 SQL 校验，某品牌铺市率 99.64%，期望区间 60–92%。

**根因** 生成器让每个有效终端都从全量 116 个 SKU 里抽样铺货，
于是不存在"这家店不经营这个品牌"的情况。而**铺市率的缺口恰恰全部来自这里**——
竞品专营、渠道不匹配、经销商尚未开发。

**解法** 加两层机制：渠道级品牌覆盖概率（大卖场 0.97 / 传统食杂 0.60 / 餐饮 0.52），
以及 6% 的"有效但未铺货"终端。降到 65.1%。

**一般结论** 造数据时，先问"这个指标为什么不是 100%"，
答案里的机制就是必须建进生成器的东西。分母写对了不代表分子有缺口来源。

### 1.2 单店产出 大卖场 / 传统食杂 = 60 倍

**现象** 期望 15–30 倍，实测 60.4 倍。

**根因** 两层系数独立叠加后失控：渠道系数差 8.6 倍 × 门店等级分布差 2.7 倍 = 23 倍速度差，
再乘上铺货品项数差 3.4 倍（92 个 SKU vs 27 个），总差 78 倍。
**我只校准了单层系数，没有校准复合效应。**

**解法** 把渠道系数从 3.6/0.42 收敛到 2.6/0.72，等级系数从 2.2/0.50 收敛到 1.9/0.62，
落到 22.4 倍。

**一般结论** 多个乘性系数叠加时，必须对**最终可观测指标**做校准，
而不是分别对每个系数拍脑袋。

### 1.3 拜访达成率 102.9%

**现象** 超过 100%。

**根因** 这个口径本身允许超 100%——计划外的临时拜访计入分子不计入分母，
`metrics.yaml` 的 caveat 里就是这么写的。但 12% 的计划外比例不真实，
现实中业务代表的临时拜访约 5%。**口径没错，参数错了。**

**解法** 计划外比例降到 6%，达成率落到 94.5%。

**一般结论** 指标越界时先分辨是**口径定义问题**还是**数据参数问题**，
两者的修法完全不同。这次若去改口径就错了。

## 二、检索与缓存

### 2.1 ⭐⭐ 纯向量做语义缓存是错的（本项目最值得讲的一条）

**现象** 设计语义缓存时想用「问题向量相似度超阈值即视为同一问题」，
先做了一组实测验证阈值该定多少。

**数据** bge-small-zh 上，与「华东区上个月的销售额是多少」的余弦相似度：

| 探测问句 | 相似度 | 应否命中 |
|---|---|---|
| 华东区**这个月**的销售额是多少 | **0.9824** | 否 |
| 华东区上月销售金额多少 | 0.9674 | 是 |
| 华东区上个月的**销量**是多少 | 0.9455 | 否 |
| 华东大区上个月销售额 | 0.9370 | 是 |
| **华南区**上个月的销售额是多少 | 0.9318 | 否 |
| 上月华东的销额是多少 | 0.8967 | 是 |
| 华东区上个月的**铺市率**是多少 | 0.8162 | 否 |
| 帮我看下华东上个月卖了多少钱 | 0.8141 | 是 |

**根因** 两组分布**完全重叠**，且「换时间」那条比所有真同义句都高。
原因是区分查询语义的恰恰是「华东/华南」「上月/本月」「销售额/销量」这类
**低信息量 token**，而句向量被句式结构主导。**没有任何阈值能切开。**

**解法** 三元指纹作硬闸门：规则抽取「指标 id + 维度取值 + 归一化时间」，
指纹不一致直接判为不同查询，向量只在指纹相同的前提下消化措辞差异（阈值放宽到 0.88）。
实测 3/3 命中同义句、4/4 拒绝伪同义句，命中延迟中位 5ms。

**一般结论** 向量相似度衡量的是「像不像」，不是「等不等价」。
凡是**替换少量 token 就改变语义**的场景（数据查询、代码检索、法条匹配），
都不能只靠向量。而缓存误命中会把错误结果直接送到用户手里，代价远高于不命中——
**这类场景的默认策略应该是宁可漏，不可错**。

### 2.2 ⭐ 指纹匹配：子串判重处理不了重叠

**现象** 「华东区上个月的销售额」抽出的指纹里同时有 `region=华东` 和 `district=东区`，
导致它和「华东大区上个月销售额」被判为不同查询。

**根因** 我用「该取值是否已被消费过的字符串包含」来判重。
但「华东」(0-2) 与「东区」(1-3) 是**重叠**关系而非包含关系，
子串检查完全失效。同类问题还有两处：`2026年8月` 被年份模式重复匹配产出两个时间标记；
`新品铺市率` 被 `铺市率` 抢走。

**解法** 改成基于字符区间的最大匹配：收集全部候选的 (start, end)，
按「起点升序、长度降序」贪心接受不重叠者。一次修好三类问题。

**一般结论** 词典匹配的去重必须在**位置空间**做，不能在字符串空间做。
「左优先 + 长优先」是分词与实体识别的标准贪心策略，遇到嵌套/重叠一律先想它。

### 2.3 jieba 默认词典不认领域术语

**现象** 「铺市率」被切成「铺」+「市率」，「传统食杂」被切碎，BM25 完全召不回。

**解法** 把 `metrics.yaml` 的全部指标名与别名、维度取值字典、以及手写的行业术语表
（共 369 条）灌进 `jieba.add_word`。

**一般结论** 中文稀疏检索里，**领域词典是必需品不是优化项**。
上线前必须打印一遍真实 query 的分词结果肉眼过一遍。

### 2.4 token 被重复计入词频

**现象** 分词结果里每个词出现两次。

**根因** 为了把 `fact_promo_cost` 再切成 `fact/promo/cost`，
我对所有 token 都跑了一遍 `split("_")`——不含下划线的词返回自身，于是全部翻倍。

**解法** 只对含 `_` 或 `.` 的 token 做二次切分。

**一般结论** 影响不大（所有文档均匀膨胀，BM25 排序基本不变），但属于自己给自己
埋雷：一旦后续加入基于绝对词频的逻辑就会出错。

## 三、口径与跨粒度

这一类的共同特征是：**SQL 语法正确、执行成功、返回了数字，但数字是错的。**
业务方看不出来，测试也测不出来（没有异常抛出）。**这是数据问答里最危险的一类问题。**

### 3.1 ⭐⭐ 费效比的跨粒度 JOIN

**现象** 问「2026年8月哪个大区的费效比最高」，两次运行分别返回 **61.69** 和 **1.11**。
基准校验的整体费效比是 5.60。两次都执行成功，都返回了合理格式的数字。

**根因** `fact_promo_cost.date_key` 固定为**归属月首日**，`fact_sales` 是**日粒度**。
模型按 `date_key` 直接关联，于是**只有每月 1 号能匹配上**。
匹配到的费用极少 → 费效比虚高；LEFT JOIN 的行为随 SQL 写法波动 → 结果不稳定。

我的 caveat 原文是「关联前须先各自按月聚合再 JOIN」——**说了，但模型没照做**。

**解法** 把 caveat 从一句告诫改成**一段可照抄的完整 SQL 范式**（两个 CTE 各自聚合到
`year_month` 再 `USING (year_month, region)` 关联）。改完稳定返回 5.90。

**一般结论** 两点。
一是**同名字段不等于同粒度**，`date_key` 在四张事实表里含义各不相同，
这类隐式契约必须显式写进 semantic layer。
二是给 LLM 的约束，**"告诉它不要做什么" 远不如 "给它一段照抄的范式"**。
前者是让模型自己推导正确写法，后者是把推导结果直接给它。

### 3.2 ⭐ 动销率的终端级口径在跨单品提问时塌成 100%

**现象** 问「上个月碳酸饮料品类的动销率」返回 1.0。

**根因** 我把动销率定义成「有销量的终端数 / 铺货终端数」。
这个定义在**问单个 SKU 时正确**，但跨多个 SKU 提问时，
一家店只要卖出任意一支商品就算"动销"，必然接近 100%，完全失去业务含义。
**真正卖不动的是某家店的某个单品，不是整家店。**

**解法** 改成「终端 × 单品」组合级，并在 caveat 里明确要求
分母必须施加与分子完全相同的商品筛选。改完碳酸饮料返回 99.79%（旺季快消品，合理），
全品类均值 91.6%。

**一般结论** 定义指标时要检验它在**不同聚合层级下是否都保持业务含义**。
一个在 SKU 级正确的口径，在品类级可能退化成常数。

### 3.3 `do` 是 DuckDB 保留字

**现象** `Parser Error: syntax error at or near "do"`。

**根因** 模型把 `dim_outlet` 缩写成 `do` 作表别名。DuckDB 沿用 PostgreSQL 语法，
`do` 是保留字。

**解法** 在 prompt 里给出别名规范（`dim_outlet` → `o`，`fact_sales` → `s` 等），
并列出禁用词。

**一般结论** 模型生成标识符时不会检查保留字。凡是让模型自由命名的地方
（别名、临时表名、CTE 名），都要么给定命名规则，要么在护栏层校验。

## 四、并发与资源

### 4.1 ⭐ Qdrant 嵌入式排他锁 × 线程池竞态

**现象** `Storage folder ... is already accessed by another instance of Qdrant client`。

**根因（两层）**
第一层：Qdrant 嵌入式模式对存储目录持**排他文件锁**，全进程只能有一个 client。
而我的语义缓存和 schema 检索各自 `QdrantClient(path=...)` 了一次。
第二层（更隐蔽）：改成 `lru_cache` 单例后**依然报错**——
因为 **LangGraph 的并行节点跑在线程池里**，三路召回同时进入缓存未命中分支，
各自构造了一个客户端。`lru_cache` 只保证结果被缓存，**不保证构造过程互斥**。

**解法** 双重检查锁（module 级 `threading.Lock` + 两次 `is None` 判断）。

**一般结论** 两条。
一是**「无服务端」的代价是失去并发能力**，这是 8GB 无 Docker 环境下选嵌入式方案
必须接受的约束，选型时就该知道。
二是 `lru_cache` / `@cache` **不是线程安全的单例工厂**。
凡是构造过程有副作用（开文件、占端口、持锁）的对象，都必须显式加锁。

### 4.2 DuckDB 每线程连接导致解释器退出时崩溃

**现象** 程序输出完结果后 `libc++abi: terminating due to uncaught exception:
recursive_mutex lock failed`。

**根因** 我给每个线程开了一个独立的只读连接。这些连接在解释器关闭时
以**不确定顺序**析构，在 LangGraph 线程池场景下触发 DuckDB 内部互斥锁错误。

**解法** 改成官方推荐的并发读模式：**单一底层连接 + 每线程 `cursor()`**，
并用 atexit 显式关闭根连接。

**一般结论** 「每线程一个连接」是关系型数据库的习惯做法，
但嵌入式数据库（DuckDB / SQLite）通常是「一个连接 + 多个游标」。
照搬习惯之前先查文档的并发章节。

## 五、多轮上下文

### 5.1 ⭐ history 存原始问句导致上下文逐轮衰减

**现象** 四轮对话，第四轮「只看便利店渠道再算一次」的结果是 26.8 万，
而正确答案（承接第一轮的"上个月"）是 1.6 万。**量级错 17 倍，执行完全成功。**

**根因** 我把**用户的原始问句**写回 history。第三轮的原句
「这两个大区哪个单店产出更高」本身不含时间，进了 history 之后，
第四轮改写时能看到的最近上文里就没有时间信息了，
第一轮的「上个月」隔了三轮已经衰减掉。

**解法** history 存**改写后的完整问句**。改写节点的产物既给下游用，也回灌上文，
使每一轮的上下文都是自包含的。

**一般结论** 指代消解的产物必须回写到对话历史，否则「消解」只对当轮有效，
上下文会随轮次线性衰减。这是**架构选择**：
把改写节点放在链路最前端 + 产物回灌 history，后续所有节点都不必关心多轮。
若把多轮上下文一路透传到 SQL 生成，每个节点都要处理省略语义，出错面成倍扩大。

## 六、评测方法

这一类问题的特殊之处：**它们产出的不是报错，是一个看起来完全正常的假数字**。
链路的 bug 至少还会返回一个业务上离谱的值，评测的 bug 连这点线索都没有。

### 6.1 ⭐⭐ API 故障被计入模型失败

**现象** 评测跑到中途准确率从 78% 掉到 36%，第三轮直接 0%。

**根因** 评测器的 `except` 把所有异常都归为「语法错误」，于是 429 限流、
402 欠费、连接超时全被算作「模型写错了 SQL」。第一轮的 74% 里就混着 4 个 429——
**如果我没去看错误详情，会直接把这个被污染的数字写进简历。**

**解法** 三层：API 故障单独归类不计入模型失败；单组 API 故障率超过 2% 直接中止
评测并抛出首个原始错误；并发从 8 降到 4（DeepSeek 按余额分配并发额度，上限 5），
LLM 层加 429 指数退避重试。

**一般结论** 评测代码里**基础设施故障与被测对象的失败必须严格分开**。
任何把两者混在一个 except 里的写法，都会在压力最大的时候（并发高、余额低、
网络差）安静地压低指标。评测器本身要有「拒绝出数」的能力，
出一个不可信的数字比不出数字危险得多。

### 6.2 ⭐⭐ 输出列约定未规定，导致大量误判

**现象** 首轮评测总体 62%，其中最简单的第一档只有 76%——**最简单的题错得最多，
这几乎必然说明是评测本身有问题**。

**根因** 问「哪些品牌的净销额占比超过百分之十」，我的 gold 只返回品牌名，
模型返回品牌 + 销额 + 占比。问「同比增长了多少」，gold 返回一个数，
模型返回本期、同期、差额、增长率四列。**两边都对，但按执行准确率的严格口径判错。**
根本原因是「该返回哪些列」这个自由度从未被规定，gold 和系统各按各的理解来。

**解法** 不是放宽比对标准（那是凑分），而是把约定写进 prompt：
「只返回回答问题所必需的列，问『哪些 X』只返回 X 的标识列，
问『多少/比例』只返回该数值列」。**基线也加同一条，否则消融不公平。**
改完从 62% 升到 78%，第一档 76% → 100%。

**一般结论** 评测里出现「简单题错得比难题多」时，先查评测不要先查模型。
另外：凡是评测中存在的自由度，要么在指令里消除，要么在比对里容忍，
不能一边不说一边严判。

### 6.3 ⭐ gold SQL 自身的歧义

改了六处，全是我写 gold 时想当然：

| 题 | 我的 gold | 模型的写法 | 谁对 |
|---|---|---|---|
| 每个渠道有多少家终端 | 全部终端 | 加了 `WHERE is_active` | **模型对**，schema 里就写着「is_active 是否有效终端」 |
| 促销与非促销的销额 | 输出布尔值 | 输出「促销期/非促销期」 | 都对，是渲染歧义 |
| 各大区业务代表的拜访次数 | 按大区分组 | 按大区+人分组 | 问题本身没说清 |
| 前 20% 的单品 | `rn <= tot*0.2` | 用了 CEIL | 都对，切分口径歧义 |

**解法** 前两类改问题措辞消除歧义（「有效终端」「占比是多少」），
后两类改成不可能有二义的表述（「前二十的单品」）。

**一般结论** 自己出题自己写 gold 时，最大的风险不是写错 SQL，
是**把自己脑子里的隐含假设当成题目的一部分**。判断标准很简单：
如果模型的答案在业务上也说得通，那就是题出得不好，不是模型答错。

### 6.4 ⭐ 单轮评测不足以支撑消融结论

**现象** 同一配置重跑两轮，总体准确率 78% 与 77%，看似稳定；
但**逐题比对发现 9 道题翻转**。

**根因** temperature=0 不等于确定性输出。而消融的差值（混合检索 −1～−3、
self-correction +1～−2）**小于轮次波动幅度**，单轮结果无法区分「真实贡献」
与「随机抖动」。

**解法** 每组配置独立跑三轮取均值并报告区间；差值小于波动幅度的一律标注
「落在波动内，不构成有效差异」，而不是当成贡献写进结论。

**一般结论** 报消融必须报波动。只给一个差值不给波动幅度，
等于宣称精度高于测量本身能达到的水平。这也是简历里写「贡献 X 个百分点」
最容易被问穿的地方——面试官问一句「跑了几轮」就够了。

## 七、归因算法与合成基准

这一节的三条都不是「代码写错了」，而是**衡量方式选错了**——
算法本身没问题，但用错的尺子去量，得到的结论会完全反过来。

### 7.1 ⭐⭐ 集中度指标被反向对冲骗过

**现象** 归因引擎要在 8 个候选维度里选「最有解释力」的那个来拆解。
我最初用「达到 80% 累计贡献需要几个取值」衡量：越少越集中。
实测 2026-07 → 2026-08，大区维度**头名贡献 +246.6%，集中度算成满分 1.000**。

**根因** 这两个月净变动只有 +1.1%，分母趋零把所有贡献度都放大了。
真实情况是某大区涨了 246%、其余合计跌了 146%——**这是强烈的内部对冲，
不是集中**。而累计贡献一个取值就超过 80%，指标看起来完美。

**解法** 换成对「移动量份额」计算的**归一化 HHI**：
`share_i = |delta_i| / Σ|delta_j|`，`HHI = Σ share_i²`，
再按取值个数归一化 `(HHI − 1/n) / (1 − 1/n)` 使不同基数的维度可比。
同时单独报告**净额/毛额比** `|Σdelta| / Σ|delta|`，低于 0.25 时标注
「变动主要由内部对冲构成，结论需谨慎」。并加显著性门槛：总变动不足 2% 直接不归因。

**一般结论** 凡是**分母可能趋零**的比率型指标，都要问一句
「分母很小的时候这个指标还有意义吗」。这里的贡献度就是典型：
它在总变动显著时是精确分解，在总变动趋零时是纯噪声放大器。
补救办法不是换公式，是加显著性门槛 + 用一个不依赖该分母的辅助指标交叉验证。

### 7.2 ⭐ 判定按标签字面匹配，把正确答案判成漏判

**现象** 40 组埋因场景首轮只中 34 组，**6 组漏判全是同一类**：
埋的是「品牌=鲜果道」，引擎报的是「品类=果汁」。

**根因** 我造数据时每个品牌只归属一个品类（清源→饮用水、鲜果道→果汁……），
所以这两个维度取值**选中的是完全相同的行**。引擎报哪个都同样正确，
但我的判定要求 `(维度, 取值)` 字面相等。

**解法** 判定改为**切片等价**：把每个 `(维度, 取值)` 归一到它覆盖的实体集合
（终端轴的 outlet_id 集合，或单品轴的 sku_id 集合），集合相等即视为命中，
并在报告里注明「引擎报为等价切片 品类=果汁」。改完 34 → 39 组。

**一般结论** 自建基准里，**判定标准必须按语义等价而非字面相等**。
两个功能上不可区分的维度，要求模型猜中你心里那个标签是没有意义的。
更彻底的做法是让数据本身不存在这种一一对应（真实品牌本就跨品类），
但那要重新生成全量数据并重跑此前所有评测，代价过大，故记录为已知限制。

### 7.3 ⭐⭐ 合成基准太干净，准确率虚高到不可信

**现象** 修完 7.2 后准确率变成 **97.5%**。

**根因** 埋因注入 3%–12% 的影响，而基线两个月之间的自然波动只有 1.1%——
**信噪比高到不真实**。真实数据里每家店、每个单品的月度销额本就会自然浮动，
归因要做的正是从这层噪声里分离信号。基准里没有噪声，测的就不是归因能力。

**解法** 两步。
一是加**终端级 10%、单品级 7% 的对数正态月度波动**，按两个轴施加，不偏袒任何维度。
二是把三类场景的**总注入量拉齐在 5%–9%**——原先单因给 2%–8%、跨维双因给两个
3%–6%（合计 6%–12%），测出来「单因 75% 比跨维双因 88% 更难」，
其实只是单因的信号更弱。拉齐后准确率 85.0%，难度梯度回到正常：
单因 100% → 同维双因 75% → 跨维双因 62%。

**一般结论** 自己造的基准，**准确率过高比过低更危险**——它意味着题目没测到真问题。
看到 95% 以上先怀疑基准，别急着高兴。另外做对照实验时，
**只能有一个变量**：想比较「场景类型」的难度，就必须先把信号强度控制住。

### 7.4 注入强度要按目标影响量反推

**现象** 给只占 2% 份额的单品打七折，总盘只动 0.6%，落在自然波动里。

**解法** 先算该取值在大盘中的份额 `s`，要制造 `I` 的总盘影响，
系数即 `1 + I/s`；系数越界（<0.3 或 >3）则换一个取值。

**一般结论** 合成基准的参数应该按**想测的效应量**反推，
而不是直接给一个感觉合理的百分比。否则不同题目的实际难度天差地别，
汇总出来的准确率没有意义。

## 八、服务化与前端

### 8.1 MCP SDK 从 1.x 到 2.x 的破坏性改名

**现象** 照 `from mcp.server.fastmcp import FastMCP` 写，直接 ModuleNotFoundError。

**根因** mcp 2.x 把 `FastMCP` 改名为 `MCPServer`（`mcp.server.mcpserver`），
装饰器与返回结构也变了：`CallToolResult` 的字段是 `structured_content`
（v1 是 `structuredContent`），且返回 `list[dict]` 时会拆成多个 TextContent 块，
不是一个 JSON 数组。

**解法** 错误信息本身给了迁移指引，照做即可。值得记的是**验证方式**：
我第一次写的自测脚本用 `len(json.loads(content[0].text))` 判断指标数量，
得到 8 而不是 12——因为 `content[0]` 是第一项指标（一个 8 个键的 dict），
不是整个列表。**测试脚本本身写错，比被测代码写错更容易骗过自己。**

### 8.2 SSE 不能用 EventSource

**现象** 前端要做逐节点流式展示，第一反应是 `new EventSource('/api/ask')`。

**根因** EventSource **只支持 GET**，而问数请求带多轮上下文，
放 query string 既超长又难编码。

**解法** `fetch` + `ReadableStream` 手工解析 SSE 帧。要点是
**最后一段可能是半帧，必须留在缓冲区等下一片数据**，
否则高并发或大结果集下会随机丢事件——这类 bug 在本地小数据量下测不出来。

### 8.3 多轮改写把两句拼接

**现象** 界面上显示「指代消解后：华东区上个月的净销额是多少？那华南呢？」。
SQL 结果是对的（两个大区都返回了），但改写产物明显不是一个独立问句。

**根因** prompt 只说了「改写成不依赖上文即可独立理解的完整问句」，
模型理解成「把上文和新问题拼起来就独立了」。

**解法** 在 prompt 里给**正反例**：明确写出「反例：…？…？——这是两句，错」。
对 LLM 的约束，**给一个错误示范比多写三条规则有效**，这和第 3.1 节
「示范优于告诫」是同一条经验。

### 8.4 前端一直卡在「执行中…」——SSE 分帧按 `\n\n` 切

**现象** 后端起好了，页面头部「数仓在线 · 12 项口径 · 91 个字段」正常渲染，
说明普通 JSON 接口没问题。但点任意问题后，卡片永远停在「执行中…」，
11 个节点 chip 全是灰色 pending，浏览器不报错、不超时。

**根因** 一开始怀疑过 4 个方向：残留 uvicorn 进程抢 Qdrant 文件锁、
首次请求懒加载 AskService 太慢、dist 是旧包、代理缓冲。
先用 `curl -sN -o file -w "%{http_code} %{time_total}"` 打后端：
HTTP 200、**8 毫秒、657 字节完整返回**（缓存命中），后端全无问题，
四个猜想一次性排除——**问题必在前端解析**。

再把 curl 存下的原始字节用 `od -c` 打出来，一眼看到分隔符是：

```
...5824}  \r  \n  \r  \n   e   v   e   n   t   :  ...
```

sse-starlette 发的是 **CRLF**，而 `api.ts` 里写的是 `buf.split('\n\n')`。
`\r\n\r\n` 里两个 `\n` 中间隔着一个 `\r`，**永远匹配不上 `'\n\n'`**，
于是所有帧都被当成"半帧"留在缓冲区，`onEvent` 一次都没触发。
而 `running` 只在 `done` 事件里清掉，所以界面永久停在执行中。

**解法** 按 SSE 规范允许的三种换行分帧，行内也同样处理：

```ts
const frames = buf.split(/\r\n\r\n|\n\n|\r\r/)
buf = frames.pop() ?? ''
const line = frame.split(/\r\n|\n|\r/).find((l) => l.startsWith('data:'))
```

对整个缓冲区（而不是单个 chunk）做正则切分，是为了兼容
**chunk 边界正好落在 `\r` 和 `\n` 之间**的情况——此时 `\r` 留在 buf 里等下一片，
不会被误判成一个 `\r\r` 帧界。用抓到的真实字节流按 1/3/7/64 字节切片回放验证，
四种切法都稳定还原出 `cache_hit → sql → rows → done`。

**教训** 三条：

1. **先用 curl 把前后端切开。** 一个带 `%{http_code}` 和 `%{time_total}` 的 curl，
   8 毫秒就把四个猜想同时判死了；否则很可能先去 kill 进程、清 dist、加日志，绕一大圈。
2. **协议层的 bug 要看字节，不要看文本。** 我更早一次测试用 `grep -c "^event:"`
   数出 14 帧，结论是"后端 SSE 正常"——完全正确，但 `grep` 恰好把 `\r` 藏掉了，
   于是同一个证据反而**加固了错误的方向**。`od -c` / `cat -v` 才看得见真相。
3. **别只按自己那一端的实现写解析。** 8.2 里我已经想到"半帧要留缓冲区"这种边界，
   却没想到换行符本身有三种合法写法——**规范里的可选项，就是跨实现联调的雷。**

## 复盘：这些问题的共性

1. **最危险的 bug 不抛异常。** 3.1、3.2、5.1、6.1、6.2 全都是"执行成功但结果错误"，
   靠单元测试发现不了，只能靠**对业务数值量级的直觉**加上基准校验。
   这也是为什么要先写 14 条基准 SQL 再写链路。
   其中 6.1 和 6.2 更危险一层：错的是评测本身，连业务直觉都用不上，
   只能靠「简单题错得比难题多，不合常理」这种结构性反常去发现。

2. **对 LLM 的约束，示范优于告诫。** 3.1 里 caveat 说了"须先按月聚合"模型没照做，
   换成一段可照抄的 SQL 就对了；8.3 里加一个反例，比多写三条规则管用。

3. **缓存与检索的失败模式是不对称的。** 漏命中只是慢一点，错命中是给出错误答案。
   设计阈值时要往"宁可漏"的方向偏。

4. **单例与并发的坑集中在"构造过程"而非"使用过程"。** 4.1、4.2 都是如此。

5. **造数据比查数据难。** M1 花在校准数据真实性上的时间远超建表本身，
   但正是这部分让后面所有的数字都站得住。

6. **评测器要有拒绝出数的能力。** 出一个不可信的数字，比不出数字危险得多。

7. **衡量方式错了比代码错了更难发现。** 第七节三条全属此类——
   算法没问题，但尺子选错，结论会完全反过来。判断方法只有一个：
   拿一个你**已知答案**的极端案例去量（净变动趋零、两个等价维度、无噪声环境），
   看指标给出的答案是否符合常识。
